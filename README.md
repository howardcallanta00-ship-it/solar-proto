# SolarFlow

## Run it
No install needed. Unzip, then either:
- double-click `index.html`, or
- from this folder run `python3 -m http.server 8080` and open http://localhost:8080

## Try this demo path (use the "Signed in as" selector, top right)
1. **Customer** → a four-step flow: *Your home* → *Template* (Essential / Recommended / Premium) → *Fine-tune* → *Review*. In Fine-tune, click empty roof slots or battery slots (or use + / −), drag through the day to see solar, battery and grid, and watch the bill panel on the right move. Then send it to the engineer, as is or customized.
2. **Site engineer** → Project pipeline → open the new project → approve. Then **Intake/permit staff** approves (stage 1).
3. **Engineer** then **Manager** approve the quotation (stage 2). **Staff** release it (stage 3).
4. **Customer** → My project → accept quotation → upload requirements (simulated OCR).
5. **Staff** → submit permit package. **Manager** → assign a technician. **Technician** ticks milestones. **QA** turns over.
6. **Customer** → My bill insights (demo accounts P-1004 and P-1008) and **Manager / Management** → Analytics, Analytics spec.

## Files
- `model.js` sizing and energy-balance math (assumptions at the top)
- `data.js` seed projects and SIMULATED analytics data
- `app.js` screens, roles, approval gates
- Data persists in your browser (localStorage). "Start over" clears it.

## Honest limits
All analytics data is simulated; rates, prices and permit requirements are placeholders to validate with the client.

## Round 2 additions
- Customer flow is now five steps: Your home (bill by photo/file/typing with a *simulated* reading, roof size, direction, shade, roof plan to scale), Your goal, Pick a design, Fine-tune, Review.
- Calculations stay deterministic (`model.js`): area-based panel limit (`roofFit`) and a brute-force goal solver (`solveGoal`). Explanations are template text built from those numbers, not generated by a language model.
- Fine-tune has a first-run guide, a "Words explained" glossary, units and estimate ranges.
- Engineer contacts the customer first, then does the site checklist and sends a proposal (always, even with no changes). The customer only agrees or asks a question and never has to fix the design. The quotation is made after they agree. Design versions (v1 customer, v2 engineer), customer proposal screen, change log, new pipeline states and a Design changes analytics tab.
- Saved-data key bumped to `solarflow_v6`; use Reset demo data if an older version is cached.

## Zenith: CPM analytics for delay prioritization
- Title: AI-Assisted Web-Based System for Solar Pre-Service Assessment and Job Fulfillment Management with Design-Based Cost Optimization and Critical-Path Method (CPM) Analytics for Delay Prioritization.
- `cpm.js` is the pure scheduling module (forward/backward pass, slack, slip, ranking, recommended action). `node cpm.test.js` checks the brief's numbers (critical path 18 days; scenarios A, B, C; ranking A, B, C).
- Durations are per-utility assumptions in `data.js` (`DURATIONS`); the promised install start (14 days) is frozen at quote acceptance. CPM ignores crew capacity except the technician's next free day.
- The "agent" is rule-based and simulated; every action waits for a human Approve. The demo clock (advance day) and delay buttons are labelled simulated.
- Design-based cost optimization: the engineer review shows the cost-optimality gap against the lowest-cost design meeting the same goal.
- Removed: expectation-gap tab, variance warnings, stage-6 variance card. Kept as a supporting view: Bill insights.
- Demo path: Manager > Analytics > Zenith (see ranking A, B, C) > open a job > Schedule tab > Delay 3 d / Advance day > Approve an agent action.
